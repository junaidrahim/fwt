# Public Bazel monorepo checkout benchmark

Measured September 14, 2026 (Asia/Kolkata); started 2026-09-13T19:36:15.358644+00:00.

## Result

Medians of six measured checkout creations per mode, after one warm-up each.
“Full / fwt” divides the unrounded medians. These are selected editing/review
profiles, not equivalent full checkouts or verified Bazel build environments.

| Repository | Files: full → sparse | Full Git | Native sparse Git | fwt sparse | Full / fwt |
| --- | ---: | ---: | ---: | ---: | ---: |
| [TensorFlow](https://github.com/tensorflow/tensorflow/tree/4acac40ffb5029edf3c0f98a4a50721ff8b26b95) | 36,947 → 2,278 | 2.653 s | 0.201 s | 0.248 s | 10.7× |
| [CockroachDB](https://github.com/cockroachdb/cockroach/tree/8812064a015d2faf99d3fc7e15880f94042954b0) | 20,517 → 2,043 | 1.738 s | 0.210 s | 0.260 s | 6.7× |
| [Envoy](https://github.com/envoyproxy/envoy/tree/1dc43a3ace95e03b3f26a50114d72d3b21a2bf7d) | 14,573 → 570 | 1.168 s | 0.093 s | 0.145 s | 8.1× |
| [Bazel](https://github.com/bazelbuild/bazel/tree/24dab1f320b42ca5f6d43c57fea4680cf4e02900) | 13,267 → 830 | 1.097 s | 0.112 s | 0.163 s | 6.7× |

For these profiles, fwt materialized 570–2,278 tracked paths instead of
13,267–36,947. Native sparse Git was faster than fwt by approximately 47–52 ms
at the median. The gain over full checkout comes from Git sparse checkout;
fwt adds reusable profiles, validation, and orchestration. Results do not
establish a universal speedup, build speedup, or a benefit from Rust itself.

## Environment and method

- CPU: Apple M4; memory: 16 GiB; macOS 26.1, arm64.
- Storage: APFS on the internal SSD. No physical-block savings claim.
- Git: git version 2.50.1 (Apple Git-155); Python: 3.14.7.
- Rust: rustc 1.97.1; binary built with `cargo build --locked --release --bin fwt`.
- fwt: [`e0845bb`](https://github.com/junaidrahim/fwt/commit/e0845bbce2a49b96843a59afa74dabc59978982b), reporting `fwt 0.1.0`.
  This is a build of that commit, not a test of the earlier crates.io artifact;
  measured runtime source was clean. Binary SHA-256: `1f9178a3885c2a896d290e5191fb7f70e29d49850a18e4557de1ee6318a9b560`.
- Warm/uncontrolled OS caches on a developer laptop. No cache flushing.
- Sources: clean, full, pinned depth-one Git snapshots; clone/fetch excluded.
  All tracked snapshot blobs are local before timing; no submodules or LFS payloads.
- One warm-up per mode, then six trials; starting mode rotates. Timed work is
  sequential and starts after all parallel downloads have finished.
- All modes create a new branch at the same source commit. Native sparse uses
  the same directory list and checkout sequence as fwt, including enabling
  worktree config. Raw JSON records the exact commands and run order.
- Seeding disabled (`FWT_SEED=''`); no `fwt tune`, hooks, global/system Git
  configuration, or automatic Git maintenance. User dotfiles are untouched.
- Creation only: profile setup, validation, file accounting, cleanup, Bazel
  queries, network downloads, and compilation are not inside the timer.
- Every trial passed revision, clean-status, and materialized-path checks.
  Sparse trials also passed cone and sparse-index configuration checks.
  Native sparse and fwt materialized identical path sets and logical bytes.
- **No Bazel build was attempted or verified.** Profiles were selected manually
  for editing/review, not derived from a dependency graph. Startup/analysis,
  dependency fetching, build correctness, COW, and listing performance are
  outside this experiment.
